# scrapio v2.2 产品规划与需求

> 状态：产品方案草案，供原型、需求评审和实施拆分使用。
>
> 目标用户：自用或小团队，单实例部署。产品由 scrapio、scrapio-browser 和 PostgreSQL 组成。
>
> 与 v2.1 的关系：继承“从目标页面持续得到可信数据”的目标；重新设计对象、操作路径、界面和验收方式。本文不要求复用 v2.1 的表、API、工作流定义或页面。
>
> 历史边界：现有爬虫、任务、数据、下载能力及其表保留原状。v2.2 默认界面不展示旧记录，不自动迁移、合并或改写它们。历史入口如何保留由实施设计决定，不能影响新产品主路径。
>
> 产品参照：以八爪鱼这类**可视化网页采集工具**作为体验参照，聚焦小规模、自用或小团队场景；不追求完整复制其功能、界面或云端规模。
>
> 配套文档：[功能范围与验收清单](采集平台v2.2功能范围与验收清单.md)补全交互、会话、数据交付和异常边界；[前端管理界面重设计](前端管理界面v2.2重设计.md)定义独立新应用的页面与操作路径。先验证功能和核心交互，再制定实施计划。
>
> 接口与页面对接任务见[接口落地与页面对接待办清单](采集平台v2.2接口落地与页面对接待办清单.md)。其中路径为拟议契约，待阶段 0 验证后冻结。
>
> “动态字段怎样保存为数据表”见[动态数据表与记录模型](动态数据表与记录模型.md)：数据表是逻辑集合，业务字段以带 Schema 版本的 JSONB 记录保存。

## 1. 为什么要重新规划

v2.1 已经补齐项目、数据集、采集器、运行、样例、插件和 AI 辅助等能力，但“功能存在”不等于“从零开始容易完成采集”。用户实际需要连续解决这些问题：目标能否打开、记录在哪、字段取什么、预览是否可信、正式运行会访问多少页面、结果在哪里、下一次为什么没有数据。任何一步需要跳到内部对象或手写规则，都会中断任务。

以下是待通过试用验证的**产品假设**，不是对当前系统所有用户的测量结论：

1. 用户通常先有 URL 和想要的结果，不会先有完整的数据集 Schema。
2. 抓取、选记录、选字段、处理分页、写入和调度之间的上下文切换过多。
3. “预览成功”与“正式拿到有用数据”之间缺少明显的确认点。
4. 运行历史偏过程记录，用户仍需自己判断结果是否完整、数据是否可用、下一步该修什么。
5. 为兼容旧磁力业务保留的概念，会抬高新用户的理解成本。

v2.2 的优先事项是让用户**在页面上操作和点选**，把一个真实采集目标从第一次输入到长期使用走通。规则是用户操作后形成的可编辑结果，而不是创建任务时首先面对的表单。

## 2. 产品定义

### 2.1 一句话定位

**打开网页，点选想要的数据，确认访问步骤；scrapio 将这些操作变成可测试、可定时执行的采集方案，并持续交付可追溯的结果。** JSON 接口仍有直接配置入口。

### 2.2 核心承诺

- **像操作网页一样创建**：输入 URL 后打开可交互页面，在页面上选列表、字段和下一页；不要求先建项目、数据表或手写选择器。
- **看得见规则如何执行**：操作形成可编辑的步骤序列，每步都能在真实页面或已保存样例上重放；发布前能说明访问范围、输出字段和去重方式。
- **得到可用数据**：正式运行结束后能直接打开数据表、查看新增/变化和来源证据，能通过筛选和导出消费数据。
- **持续可靠**：定时运行有明确的预期产量、运行上限与异常提示；页面变化时从失败记录进入修复、回归和再发布。
- **逐步增强**：可视化配置完成常见网页；CSS/JSONPath 是高级修正入口，JS 处理例外，AI 用于建议和解释。建议必须在样例中验证并经用户确认。

### 2.3 不承诺的事情

- 不保证任意站点零配置可采，不自动绕过验证码、登录限制或站点策略。
- 不把任意分支/无限层级的流程画布、分布式调度、多租户权限和插件市场作为首发目标。
- 不把云盘、aria2、媒体处理作为采集主流程；它们未来可作为显式开启的下游动作。
- 不默认在每次正式采集时调用 AI，也不允许未经确认的 AI 结果直接改变发布规则。

### 2.4 与八爪鱼类工具相似的部分及小规模取舍

| 体验 | v2.2 要做 | 有意收窄 |
| --- | --- | --- |
| 可视化建任务 | 页面内点选元素、识别同类列表、自动给出字段和步骤建议 | 不保证所有网页一键识别正确，始终可手动修正 |
| 页面操作 | 在预览浏览器里点击、输入、等待和滚动，保存并回放步骤 | 首版只支持少量可验证动作，不做通用桌面自动化 |
| 流程配置 | 清晰呈现入口、动作、列表/翻页、详情、提取和输出 | 一个主流程加受限循环，不做任意节点连线画布 |
| 数据交付 | 本地 PostgreSQL 存储、查询、变化、CSV/JSON 导出 | 不建设云任务集群、代理市场和 SaaS 计费体系 |

浏览器交互式编辑是本产品的核心能力，不能用“抓取一份 HTML 后填写 CSS 选择器”代替。对于纯 JSON 接口或简单静态页面，可直接走轻量路径，使用同一预览、发布和数据结果语义。

## 3. 服务对象与成功任务

| 角色 | 首要任务 | 成功的可见结果 |
| --- | --- | --- |
| 采集创建者 | 将一个 URL 配成可持续采集方案 | 看到第一条正式数据、来源和下次运行时间 |
| 数据使用者 | 查询、比较和导出结果 | 能理解字段、更新时间和记录从何而来 |
| 维护者 | 发现并修复断掉的采集 | 能定位失败页/字段，回归通过后确认恢复 |
| 实例管理员 | 保证浏览器、数据库和容量可用 | 能区分服务故障、站点限制和规则错误 |

同一人可以承担以上全部角色。默认单实例，不引入组织/租户管理流程。

## 4. 全新的产品模型

### 4.1 用户只需先理解三个对象

| 对象 | 用户看到的含义 | 创建时必须填写 |
| --- | --- | --- |
| **采集方案** | 页面如何打开和操作、从哪里取记录、提取什么、何时再取 | 目标 URL；其余可在页面上点选并试采 |
| **数据表** | 一类可查询、可导出的结构化记录 | 首次保存前确认名称、字段和去重键 |
| **运行** | 方案的一次执行及结果 | 无；手动试运行或调度自动创建 |

页面步骤、快照、样例、字段规则、版本、页面任务和观察记录是这些对象的**详情和证据**，不要求用户在首页认识它们。多个采集方案可以写同一数据表，但须显式选择并通过字段兼容检查。项目/文件夹仅用于后期组织方案和数据表；首个方案不需要项目选择。

这里的“数据表”是用户理解的逻辑数据集合，不代表每个采集方案都在 PostgreSQL 新建一张物理表。字段随配置变化，但正式记录必须经过已发布的字段 Schema、唯一键和更新规则校验；存储、观察、修订与查询原则见[动态数据表与记录模型](动态数据表与记录模型.md)。

用户编辑的采集步骤保持固定的可理解结构：**打开入口 → 可选页面操作 → 定位记录/发现详情 → 可选翻页 → 提取字段 → 校验并保存**。每一步能在工作台中单独试行、查看输入输出和错误。列表循环和详情处理是明确的专用结构，避免用户从零搭建任意流程图。

### 4.2 两种不同的“运行”

- **试采**：可访问真实目标，也可用保存快照；会展示页面、候选记录和预计入库动作。默认不写正式数据、不触发外部动作、不占用定时计划。
- **正式运行**：固定使用一个已发布版本，遵守访问预算，写入数据和运行证据；结束后展示新增、变化、未变、无效、失败和受限范围。

界面始终标明“实时页面 / 保存快照”和“试采 / 正式运行”。保存快照回归不能被描述成真实站点可用性验证。

### 4.3 发布版本

草稿允许边编辑边试采；发布后形成不可变版本。运行固定版本，修复时复制为新草稿。字段定义、去重键、获取方式、发现规则、预算和调度条件在发布检查中一起呈现。只改调度时间无需重发提取规则，但必须留下操作记录。

## 5. 从头到尾的主路径

### 5.1 首次使用：URL 到第一条数据

1. 首页主动作“开始采集”，输入网页 URL；接口用户可切换到 JSON 入口，也可粘贴示例响应离线起步。
2. 打开工作台内的远程浏览器页面。用户可正常导航，再切换“选择数据 / 操作页面”模式；界面显示当前地址、加载状态、截图及浏览器动作回执。目标适合静态 HTTP 时可选择快速获取，但不替换浏览器点选路径。
3. 用户在页面上点击一条目标记录或一个字段；系统高亮命中元素、建议相似项，用户确认“单条数据 / 重复列表 / 详情链接”。列表页可点选下一页或“加载更多”，并限定访问范围。
4. 用户点选字段并命名，可选择文本、链接、图片地址或属性。每个字段即时展示**命中范围、样本值、原始值 → 处理后值 → 校验结果**；切换其他列表项/详情页检查规则是否稳定。CSS/JSONPath 是高级修正方式。
5. 用户需要点击、输入、等待或滚动时，在“操作页面”模式记录动作；可删除、重排、单步重放，并看到动作前后页面。涉及登录时使用受控会话，不把密码记录进动作或样例。
6. 用户确认数据表名称、字段类型、必填项和去重键。系统用当前候选数据预演新增、更新、未变、无效和冲突；默认更新规则解释为人话。
7. 用户选择一个小范围试采，例如 1 个列表页、最多 3 个详情页。结果页展示实际访问路径、每步动作、找到多少条、为什么丢弃、预计保存什么，并允许返回出错步骤继续点选。
8. 用户保存有代表性的样例，通过发布检查后发布，执行首次正式运行。
9. 完成页直接展示**实际写入的数据表和一条记录**，同时给出“看全部数据”“设置定时”“继续完善规则”。若正式运行没有有效记录，明确标记未完成并显示原因。

在这个路径中，浏览器服务、Schema 版本、页面任务 ID 和 JSON 定义均不占据主要界面；高级用户仍能查看和编辑相关细节。

### 5.2 第二天：数据有没有更新

登录后首页展示最近使用的数据表、最近有效更新、方案的下次运行、最近新增/变化和需处理的问题。点击一条变化可看到字段前后值和来源。零条新增可能是正常去重；只有与历史基线、预期数量和页面覆盖一起判断后才提示异常。

### 5.3 出问题：定位、修复、确认恢复

异常提醒 → 查看受影响的数据表/方案和最近失败运行 → 打开出错页面或 JSON 响应 → 定位字段、发现规则或获取步骤 → 将失败页面保存为回归样例 → 修改草稿 → 与已发布版本对比 → 回归 → 发布 → 手动验证一次 → 确认数据恢复。

如果没有保留原文，也应留下 URL、状态、步骤、错误和保存策略，界面说明证据缺失的原因。

## 6. v2.2 需求清单

优先级定义：**P0** 是主路径必须完成；**P1** 是持续使用所需；**P2** 是建立在 P0/P1 稳定后的增强。以下是产品需求，不按当前模块拆分。

### 6.1 P0：新用户拿到第一条可信数据

| ID | 需求 | 验收口径 |
| --- | --- | --- |
| V22-01 | URL 起步与可交互预览 | 新实例只凭 URL 打开工作台内浏览器页面；可导航并切换点选模式；显示最终地址、状态、耗时及错误分类，无须先建项目或源 |
| V22-02 | 页面点选与规则生成 | 点选元素时高亮当前命中和同类候选，显示数量与样本值；系统生成可重放的定位规则，用户能增减命中范围、撤销及手动修正 |
| V22-03 | 浏览器动作录制与回放 | 首版支持点击、输入、等待和滚动；操作可单步试行、删除及重排，结果与错误可见；登录密码不写入动作记录 |
| V22-04 | 统一取样 | HTML、JSON、浏览器页面都能保存样例；页面可视化和结构视图对应，浏览器保存截图/动作回执；标出实时与离线 |

| V22-06 | 字段提取与转换 | 在页面点选字段、命名并选择文本/属性/链接/图片地址；数字、日期、数组可基础处理；逐字段显示命中、原值、结果和错误，高级用户可编辑 CSS/JSONPath |

| V22-09 | 发布与首次运行 | 发布前检查样例和预算；正式运行固定版本；成功页打开真实记录，失败页能进入对应步骤；不能把零有效记录误报成完成 |
| V22-10 | 新产品界面隔离 | 默认导航、搜索、统计、列表及新建流程仅使用 v2.2 对象和数据；旧记录不混入计数或空状态 |

| ID | 需求 | 验收口径 |
| --- | --- | --- |

### 6.3 P2：帮助处理复杂目标

| ID | 需求 | 验收口径 |
| --- | --- | --- |
| V22-18 | 可控 JS 扩展 | 明确区分“页面内动作/脚本”和“数据转换脚本”；输入、输出、权限、超时及错误位置可测试、可追溯 |
| V22-19 | AI 辅助创建与修复 | 用户预览待发送内容并确认；AI 提供字段/定位建议和失败解释；必须在样例验证并经人工选择，费用与调用次数可见 |
| V22-20 | 外部动作 | 仅对正式提交后的记录变化显式订阅；预览不执行；有幂等、失败重试和副作用提示。云盘/aria2 是可选集成 |
| V22-21 | 多来源合并 | 新方案可选择已有数据表；字段映射与去重冲突先预览，再允许合并；保留每个来源的证据 |

P2 项目不能用来掩盖 P0 的可视化配置断点。尤其 AI 是辅助配置与诊断，不替代可重复执行的规则和验收。

## 7. 信息架构与关键页面

### 7.1 导航

```text
首页          我关心的数据、最近变化、需要处理、开始采集
采集方案      创建、编辑、试采、发布、调度及方案健康
数据          数据表、记录、来源、变化、筛选与导出
运行          最近运行、结果解释、页面证据、失败与重试
设置          浏览器连接、凭据、实例容量、成员和操作记录
```

“项目”不是一级入口；确有多个主题时，可在采集方案和数据表上加文件夹/标签。首页空状态不显示历史磁力数据，也不因旧数据库有记录就跳过新手引导。

### 7.2 采集方案工作台

同一页面保留 URL、当前样例和草稿。按用户任务组织步骤：**打开页面 → 操作页面 → 找到记录 → 提取字段 → 保存数据 → 测试发布 → 定时运行**。中央主区域是可交互的目标页面，左侧是步骤与动作，右侧是当前选中元素、匹配范围、样本值和数据预览；JSON 入口将页面换成可点选的结构树。窄屏改为页面与步骤/结果切换。顶部始终能看到草稿状态、保存、试采和发布。

页面预览有明确的“正常浏览”“选择记录”“选择字段”“录制操作”模式。鼠标悬停高亮候选元素；点击后展示选择器的稳定性提示、当前命中数与其他样本页的命中结果；用户可以扩大/缩小范围、撤销或查看生成的规则。浏览器动作在左侧按顺序呈现，支持单步重放、从当前步继续和查看动作前后页面。每一步说明未配置、待验证、通过或失败，不把“保存成功”当作“采集可用”。

高级区提供 CSS/JSONPath、规则定义和 JS；高阶配置返回可视化模式时必须保真，无法表达的规则应提示只读或转高级编辑，不能静默丢字段。AI 建议显示命中的样例值、依据和接受前后的差异。

完整页面地图、模式反馈、试采/发布、数据消费与修复路径见[前端管理界面 v2.2 重设计](前端管理界面v2.2重设计.md)。新前端采用独立应用外壳及唯一导航源，旧页面由独立旧入口承接；不能在旧后台菜单中再叠加一层新导航。

### 7.2.1 可视化编辑的交互边界

- 浏览器服务提供足以支持远程交互的页面画面/状态、元素命中、可定位标识和 DOM 结构摘要；具体采用流式画面、事件转发或其他协议由技术验证决定。界面不能仅凭截图像素生成选择器。页面变化后应能检测失配并提示重新点选。
- 在远程页面点击元素时，必须清楚区分“只是选择此元素”和“真正点击网页”。输入密码、提交表单、触发购买/发送等动作需明确授权和执行反馈。
- 记录列表的建议规则要在至少两个同类元素和多个样例上验证；仅匹配一个样本时显示证据不足，不声称规则稳定。
- 选择器仍是可维护的规则产物；用户能查看、复制和手动修改。可视化配置与正式执行用同一规则解释器。
- 无法在预览中稳定交互的页面可退回结构视图和手工规则，界面要说明失败原因与可用替代路径。

### 7.3 数据工作区

数据表首页展示字段、总量、新增/变化、最近有效更新与来源方案；记录列表支持保存筛选。记录详情先显示业务字段，再显示首次/最近观察、字段变化、原始页面和运行版本。没有数据时给出“返回采集方案检查试采/首次运行”的入口。

### 7.4 运行详情

首屏先回答：访问了多少、发现多少、有效多少、写入多少、未覆盖多少、为何停止。再展开页面树和每个页面的获取结果、字段诊断、文档/截图与错误。失败项有“在草稿中修复”，异常完成项有“查看影响的数据”。内部 ID 放到技术详情。

### 7.5 系统设置

显示浏览器服务健康、协议能力、请求容量、凭据引用、原文保留策略和 AI 配置。用户在创建时仅在能力不可用或确实需要授权时才接触这些设置。

## 8. 能力与数据的产品契约

1. **同一规则，两处执行**：试采/回归与正式运行使用相同的获取后处理、记录定位、提取、校验与去重语义；差异仅在真实网络访问、写入及外部动作是否启用。
2. **显式访问范围**：每次试采和正式运行都有 URL 范围、最大页数、最大记录数、最长时间、失败重试和请求间隔。超限以“受限结束”展示，不写成全量成功。
3. **结果可解释**：一条记录能追到方案版本、运行、页面/响应和保存决策；原文过期后保留必要元数据并明确证据已清理。
4. **Schema 可演进**：字段增加、类型改变、唯一键变化须给出对现有数据的影响预览；不能因编辑草稿隐式重写旧记录。
5. **失败不静默**：获取不到页面、匹配不到记录、必填字段缺失、浏览器动作失败和保存冲突有不同状态与修复入口。
6. **浏览器是能力，不是用户必须理解的服务**：UI 只让用户选择需要渲染/交互的获取方式；服务能力不足时拒绝发布并指出具体动作。
7. **隐私与费用可见**：发送给 AI 的内容、外部动作和可能产生的费用/副作用在确认前展示；默认关闭。
8. **点选与执行一致**：编辑器生成的元素定位规则和动作顺序必须由正式运行中的同一能力执行；用户修改规则后立即重新计算命中范围，不允许“点选看起来对、正式运行抓错”的静默偏差。

这些是新产品语义；具体数据库表和 API 路径留给实施方案设计。

## 9. 与现有系统并存

### 9.1 默认原则

- 现有爬虫、工作流、磁力/资源、下载任务和旧数据原样保留；v2.2 不以迁移它们作为上线前置条件。
- 新产品使用清晰隔离的数据域与 API 契约。新首页、新搜索、新统计和导出仅查询 v2.2 数据，避免“明明没有新方案却显示旧数据”的体验。
- 旧任务是否继续运行由现有部署策略决定；v2.2 不偷偷关闭旧调度，也不自动把旧任务接入新方案。
- 需要时可在设置中提供独立的“旧版入口/历史数据”链接，并标注其独立范围；不把旧字段和旧导航混入新工作台。
- 未来如需迁移，作为单独的**显式导入工具**设计预览、映射、冲突处理和回滚；本文不安排自动迁移。

### 9.2 实施自由度

可以重做前端路由、页面结构、API 和新数据模型。能复用的 HTTP、浏览器协议、任务租约、记录校验等代码可在证明语义一致后复用；产品需求不因已有代码的形状降低标准。新数据的持久化、运行与旧系统必须有明确边界，避免同名“记录”在两个入口互相污染。

## 10. 分阶段产品交付

| 阶段 | 交付的完整用户任务 | 必须看见的结果 |
| --- | --- | --- |
| **0：可试用原型与真实任务** | 选定 3 个实际目标：HTML 单页、JSON 多记录、需浏览器交互的列表详情；用可点击原型走查点选、动作录制、运行、修复，并验证浏览器远程交互协议可行 | 确认页面模式、点选反馈和步骤顺序；记录无法完成的步骤与耗时，冻结 P0 交互契约 |
| **A：第一条可信数据** | URL → 页面点选/动作 → 记录与字段 → 数据表 → 全链路试采 → 发布 → 正式运行 | 三类目标都能在新数据工作区看到真实记录与来源；旧数据不混入 |
| **B：持续使用** | 定时/手动运行 → 看变化 → 筛选/导出 → 看异常 | 重启后调度继续；零数据、受限、部分成功能解释；数据能被消费 |
| **C：维护恢复** | 从异常进入失败证据 → 修改 → 多样例回归 → 发布 → 确认恢复 | 不必手动复制页面和规则；旧运行可追溯，新运行恢复 |
| **D：增强能力** | 选择性接入 JS、AI 和外部动作 | 权限、费用、副作用、幂等与回归均可见，默认不开启 |

每阶段按**用户任务可完成**验收，不按页面数、API 数或节点数勾选。A 的三类目标要在实际服务环境运行；固定样例和单元测试是开发门槛，不能代替真实联调。

## 11. 验收指标

| 指标 | 初始目标与测量方式 |
| --- | --- |
| 首次有效数据时间 | 对不需登录的 HTML/JSON 目标，从输入 URL 到看到第一条正式记录，试用目标为 15 分钟内；记录每一步耗时与阻断原因 |
| 主路径完成率 | 3 个选定目标中，HTML/JSON/浏览器各 1 个均能从创建走到正式数据；浏览器目标必须通过页面点选和至少一个动作，不以模拟数据通过 |
| 可视化建任务有效性 | 在 HTML 单页和浏览器列表目标上，用户通过页面点选完成记录、字段和翻页/详情选择，常见字段不必手写 CSS；记录误选、修正次数和无法点选原因 |
| 预览一致性 | 同一样例的试采候选、校验与正式运行在相同输入下给出一致结果；写入和外部动作差异单独标明 |
| 问题定位时间 | 给维护者一例字段失效和一例浏览器获取失败，5 分钟内能定位失败阶段、原始证据及修复入口 |
| 数据可追溯率 | 新数据工作区的正式记录均可找到方案版本、运行与来源 URL；原文被清理时有明确标识 |
| 历史隔离 | 新首页、统计、搜索和导出不会出现旧采集记录；旧数据和任务仍按原方式可访问/运行 |

上述数值是试用目标，阶段 0 记录实际基线后调整；不因达到时间指标而放弃正确性和访问预算。

## 12. 待通过真实使用确定的决策

1. 首批三个真实目标及其登录/浏览器要求，以此确定浏览器动作、JSONPath、DOM 点选与跨页定位的首发范围。
2. 数据表第一次创建时，字段类型和唯一键由系统建议到什么程度；用户需在哪一步明确确认。
3. v2.2 首版旧版入口放在设置、独立地址，还是仅保留原 URL；必须先确认历史访问需求。
4. 原文、截图和样例的默认保留期，以及小团队环境的存储上限。
5. AI 是否在首发创建流程露出入口；即使露出也只提供建议，不阻塞无 AI 的完整路径。

这些决策不改变“旧数据留在原处，新产品从零完成采集”的边界。

## 13. 当前规划工作的交付顺序

1. **功能基线**：以[功能清单](采集平台v2.2功能范围与验收清单.md)确定 P0/P1/P2，补足会话、记录循环、相对字段定位、数据交付与失败恢复等主路径必需功能。清单列的是需求，不代表当前代码已交付。

3. **交互原型与技术验证**：优先验证页面点选、录制/单步重放、试采和正式数据路径。原型通过走查，浏览器通过真实目标验证，才冻结交互与协议。
4. **实施计划**：已在[接口落地与页面对接待办清单](采集平台v2.2接口落地与页面对接待办清单.md)按完整用户任务拆分控制平面、浏览器与前端交付；阶段 0 验证后再冻结接口、错误语义和验收证据并开始实现。
