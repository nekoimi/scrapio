# 下游插件交付 O5-06 实施与验收记录

> 2026-10-14：首版开发收尾。接入 aria2 请求接受回执，真实外部服务、UI走查与进程重启验收继续保留为 O5-R。部署新增迁移 `2026_10_14_004`；云盘接入暂缓。

## 1. 产品入口与交付范围

任务编辑器每个阶段的保存绑定下，新增「保存结果后交付插件」。用户选择输出端口、下载地址字段、可选 aria2 服务端目录以及触发策略。下载地址支持 HTTP、HTTPS、magnet；地址不能包含 userinfo 裸凭据。字段来源必须为该端口声明的必填、非null、非数组 string/url；API也支持显式字符串常量。服务连接及认证仍由现有 `aria2.json_rpc`、`aria2.secret` 配置提供，不进入任务输入与回执。

本轮采用阶段上的事件绑定 `stages[].deliveries`，采集器仍只负责网页/接口提取。没有新增万能插件流程节点，也不把旧资源ID或旧 `plugin_tasks` 队列混入独立编排域。复用现有插件Registry及aria2适配器，新增明确支持独立请求提交/查询的 `ReceiptHandler` 接口。

| 触发策略 | 有效持久输出的保存决策 | 使用建议 |
| --- | --- | --- |
| valid | created、updated、unchanged、passed | 全部有效输出；每次新运行可能再次交付 |
| created | created | 写表后只交付新增记录 |
| changed | created、updated | 写表端口推荐；实际变化才交付 |

仅传递端口使用valid，输出仍保存在 `co_run_outputs`。无效候选、保存冲突和未命中触发策略的输出不创建交付请求，不以「待交付」误导用户。

运行详情新增「插件交付」页，独立展示等待/提交/查询/已接受/失败/未知/结束跟踪，以及来源输出、输入、绑定指纹、GID、回执和诊断。采集完成后交付页继续刷新。按钮与确认框使用模板 Element Plus 组件。

**交付成功仅表示aria2已接受请求，不表示下载完成，也不回写文件产物。** 采集状态与交付状态独立，下载管理继续由外部服务承载。

## 2. 保存、版本与幂等

同一页事务保存业务记录、观察、运行输出、下游编排outbox、插件交付outbox及检查点。交付请求生成失败或超出容量，整页回滚；不会出现记录已保存但交付请求丢失。事务内不访问外部服务。

绑定版本固定为 `co.delivery.aria2.v1`，端口、emit、输入映射随任务manifest冻结。输出上的输入值与绑定指纹在入队时保存，worker不回读业务表当前值。修改方案需保存/发布新版本，既有运行保持原绑定。

交付幂等身份由 **运行输出ID + 绑定ID + 绑定指纹** 确定，数据库唯一约束保护同一输出/绑定。检查点重放遇到已保存输出时不会再次生成交付。O5-01合并输入共享原输出及交付；多条不同绑定可显式交付同一输出。

此语义不等于URL全局去重，也不承诺跨运行仅一次。重新运行、输出局部补采可能生成新的输出ID；同URL内容变化时changed也可能再次交付。若用户需要跨运行目标级合并，应另行定义业务身份与刷新策略。

## 3. 外部请求与未知回执

独立 `coDeliveryWorker` 单槽领取正式请求；先在事务中写入sending、固定GID、目标配置指纹与租约，再提交aria2.addUri。GID由幂等身份确定，请求强制携带该GID，不接收随意覆盖它的options。

提交前冻结服务端点与认证配置的SHA-256指纹，不保存明文配置。恢复发现配置已变化时，不向新服务查询或提交；提示恢复原配置后查原请求，或人工在原服务核对。

请求返回相同GID后记录已接受。超时、异常、回执不匹配或响应丢失时，只对原GID调用tellStatus；active/waiting/paused/complete表示已接受，error/removed表示外部已失败，未找到/无法查询不能证明此前未执行，进入awaiting_confirmation。

进程在journal后、实际提交前中断，也按未知处理：安全优先保留原GID，不自动补发。过期sending/checking租约只做查询，旧worker不能覆盖新回执。租约生成、过期和提交判定均使用数据库时间，避免主机/数据库时间差阻塞恢复。

| 用户操作 | 条件与行为 |
| --- | --- |
| 查询原回执 | 仅未知状态，使用原GID，不再次提交 |
| 确认已交付 | 用户已在外部服务核对；只记录人工确认，仍不证明下载完成 |
| 重试未提交请求 | 仅failed且没有外部ID；例如未配置插件，检查配置后显式重试 |
| 结束交付 | queued、failed或未知状态结束本平台跟踪，不撤销外部下载 |

控制接口要求confirmed、expected_revision，并复用幂等操作回执。响应丢失时查询原控制操作，不自动提交新操作。已发送或未知请求不能以retry重发；下载失败需要新交付时应由用户明确发起新运行，而不是伪装成安全重试。

暂停运行阻止queued领取；取消运行取消queued交付。已写入sending的动作视为已发出，可能继续完成，仍可核对原回执。任务采集完成不会等待交付完成，也不会因交付失败删除已保存结果。

## 4. 试采、容量与接口

实时或离线试采只生成preview及映射错误证据，插件worker仅领取formal，外部动作为0。试采不检查真实服务可用性，也不能用来证明下载成功。

每阶段最多5个交付绑定，每人最多10000个活动正式交付（queued/sending/checking/awaiting_confirmation）。页提交末尾检查积压上限，超出则回滚，不丢弃请求。输入url最多8192字节、dir最多1024字节；每次远程操作总context预算30秒、租约90秒、回执保存最多8KiB。输入、固定元数据及预留8KiB回执计入现有输出存储配额；为保守预算，不在交付完成时自动释放预留额度。数据库分页及领取/所有者积压均有索引。

| 接口 | 用途 |
| --- | --- |
| GET `/api/v4/co/delivery-capabilities` | aria2协议、是否配置、预算、试采与幂等范围 |
| GET `/api/v4/co/runs/{run_id}/deliveries` | 当前用户运行的交付游标分页 |
| POST `/api/v4/co/runs/{run_id}/deliveries/control` | 原回执查询、已接受确认、安全重试、结束跟踪 |

运行详情接口新增delivery_counts，列表及控制均按owner隔离；原采集分页接口继续保持行为。契约生成追加 `编排O0/co-o5-delivery.cjs`，旧定义缺省无deliveries，不产生新交付。

升级启动时执行迁移`2026_10_14_004`建立co_deliveries和索引，先完成迁移再启动worker。此表属于独立编排域；不迁移或重新消费旧plugin_tasks。无需新增浏览器协议或部署变量，aria2未配置时基础采集照常可用，绑定请求显示明确的未提交失败。
