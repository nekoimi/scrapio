# scrapio v2.2 动态数据表与记录模型

> 状态：产品与数据契约方案，供 v2.2 详细数据库设计使用。这里的表名和列是示意，实施时再确定 DDL、索引和迁移。
>
> 对应问题：采集规则和字段由用户动态配置，结果如何以“数据表”的方式保存、查询、去重和导出？

## 1. 先区分两种“表”

用户看到的**数据表**是一个逻辑数据集合，例如“文章”“商品”；它有名称、字段、唯一键、记录列表和导出。PostgreSQL 不必为每个逻辑数据表执行一次 `CREATE TABLE`。

建议 v2.2 使用一套独立于旧业务的物理表：

```text
collection_tables           用户创建的数据表及当前 Schema 版本
collection_schema_versions  不可变字段/唯一键/更新策略快照
collection_records          各数据表的当前记录，固定元数据列 + JSONB 字段值
collection_observations     每次采集到的原始/规范化候选与来源
collection_revisions        当前记录每次变化的前后字段
```

这是**共享物理表 + 按逻辑数据表划分**的模型。`collection_records` 的唯一约束至少覆盖 `(table_id, canonical_key)`；`collection_observations` 另有正式任务的幂等键。新数据域与现有 `datasets/records/resources/magnets` 隔离，旧数据不自动进入 v2.2 列表。

## 2. 一条动态记录如何保存

以用户在网页上点选的字段为例：

```json
{
  "数据表": "商品",
  "字段定义": {
    "url": {"type": "url", "required": true, "unique_key": true},
    "title": {"type": "string", "required": true},
    "price": {"type": "decimal"},
    "images": {"type": "url", "multiple": true}
  },
  "记录": {
    "url": "https://example.test/item/42",
    "title": "示例商品",
    "price": "19.90",
    "images": ["https://example.test/42.jpg"]
  }
}
```

`collection_records` 用固定列保存 `id/table_id/canonical_key/schema_version/status/first_seen_at/last_seen_at/created_at/updated_at`，用 `values JSONB` 保存此数据表的业务字段。价格、日期等先按 Schema 规范化，避免同一字段有时是数字、有时是文本；金额的精度规则应明确，示例中用十进制字符串表示，不靠浮点数随意比较。字段顺序和中文标签保存在 Schema，不依赖 JSON 对象的键顺序。

正式运行先产出候选记录，再按发布版本绑定的 Schema 校验/规范化，生成 `canonical_key`，在事务中写当前记录、观察和修订。观察保留候选原值、规范化值、规则版本、运行、页面/响应与时间；记录只代表**当前可查询状态**。相同键内容未变也可留下观察，用于证明这次确实检查过；内容变化才新增修订。

采集页面上出现未经确认的新字段时，不自动扩充正式数据表。可在受大小限制的观察原值或诊断中保留，提示“发现新字段”；正式记录只写入发布 Schema 声明的字段。无效候选保留受限诊断/运行证据，但不伪装成正式记录。

## 3. “动态”主要发生在配置和版本，不意味着无约束入库

用户可以随时点选新字段，但保存和发布之间有三道边界：

1. **草稿和试采**：字段可增删改，结果只是候选与预览；不要求立即修改正式数据表。
2. **首次发布**：用户确认逻辑数据表、字段类型、唯一键、必填和空值处理，生成不可变 Schema 版本；发布版本引用它。
3. **以后修改**：新增字段生成新 Schema 版本；修改类型、删除字段或改变唯一键先预演对现有记录及其他采集方案的影响，再决定新版本与历史数据处理。不能改草稿就暗中重写旧数据。

正式运行固定“采集方案版本 + Schema 版本”。如果目标数据表版本已变化且不兼容，运行应停在可解释的冲突状态或使用已批准的兼容映射，不能悄悄按最新字段解释旧版本规则。

旧记录不必因新增可选字段立即回填。读取当前表时，旧记录缺少新字段就显示“未采集”，并保留该记录最近一次写入所用的 Schema 版本；需要批量回填时另开明确任务，显示范围、进度和结果。删除字段默认只从新 Schema 的列表列定义移除，历史观察和修订仍可按当时版本读取。

需要区分**字段缺失**、**显式 `null`**、**空字符串**和**空数组**；更新策略可选择忽略缺失、保留旧值、明确清空。默认建议：缺失不覆盖已有值；显式清空需规则声明并在预览中展示。

## 4. 去重、更新和多来源

数据表必须有稳定唯一键，例如商品详情 URL、站点商品编号，或多个字段组成的复合键。键在规范化后生成；缺键候选为 `invalid`。单靠标题通常不稳定，不应默认建议为唯一键。

同一数据表的不同采集方案写入同一键时，按明确的更新策略比较字段并保存各自观察来源。首次 v2.2 可以先支持单方案单表，**多来源合并按 V22-21 交付**；物理模型预留来源证据，UI 不提前宣称可安全合并。改变唯一键需要影响预演，因为它可能导致记录合并、拆分或冲突；不自动全表改键。

保存决策应明确为 `created/updated/unchanged/invalid/conflict`。它与任务级 `failed/limited/partial` 分开；一次运行可以同时产生多种记录决策。

## 5. 如何像“表”一样查询和导出

前端根据 Schema 动态生成列、类型控件与导出列。查询 API 始终带 `table_id`，只允许按已声明字段过滤/排序；后端根据字段类型校验操作符和值，使用参数化查询。每种数据表不需要一套新 API。

PostgreSQL 的基础索引覆盖 `table_id`、唯一键、最近更新时间和稳定分页键。常用筛选字段按使用情况增加受控的表达式/生成列索引，或后续建立专门投影；不对所有动态字段自动建索引，也不开放任意 JSONPath/SQL 查询。数据量和筛选需求上来后再用实际查询计划决定优化，不把首版设计成通用分析数据库。

CSV 导出按当前 Schema 和所选列生成表头；多值字段需约定编码（建议 JSON 数组文本）；JSON 导出保留类型及 Schema 版本。大结果集异步导出，并写明过滤条件和截止时间，避免导出期间新记录使结果前后不一致。

## 6. 对页面和接口的直接影响

| 用户操作 | 后端契约 | 前端反馈 |
| --- | --- | --- |
| 在页面上新增字段 | 修改采集方案草稿的字段规则 | 即时预览候选值；尚未写正式数据表 |
| 首次确认输出 | 创建逻辑数据表和 Schema v1，绑定草稿 | 展示字段类型、唯一键、空值/更新规则与样例决策 |
| 试采 | 使用当前草稿和目标 Schema 进行 dry run | 显示 `created/updated/unchanged/invalid/conflict` 预判，不写记录 |
| 正式运行 | 使用发布版本、Schema 版本写共享记录表 | 数据表出现真实记录及来源；预判和实际结果可能因数据变化不同 |
| 增加/修改字段 | 检查 Schema 兼容性，生成新版本 | 对比旧字段/已有记录/其他方案影响；不静默迁移 |
| 查看/筛选/导出 | `table_id` + Schema 约束的分页查询 | 动态列、类型合适的筛选器和导出格式 |

这使“配置动态、存储稳定”：用户自由定义业务字段，平台仍能保证类型、唯一性、来源、历史和查询行为。当前 v2.1 的 `records.normalized JSONB`、数据集字段及 Schema 版本体现过相近方向，但 v2.2 不以复用旧表作为产品前提。
