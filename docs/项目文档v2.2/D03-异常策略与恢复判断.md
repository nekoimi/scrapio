# D03：异常策略与恢复判断

状态：开发收尾，2026-10-10；真实迁移、并发与页面联调待发版。契约 `0.21.0-d03`，迁移 `2026_10_10_011`。下一阶段 D04：凭据与授权会话。

## 产品流程

首页“异常待办”、导航“异常待办”和方案健康中的策略面板统一查询新产品问题。问题显示归因、受影响方案、首次/最近异常运行、字段和步骤、出现次数、候选恢复运行；可进入实际运行证据，从已有 D01 修复入口带入输入，继续 D02 回归/比较和发布。

策略按方案保存，独立 revision 防并发覆盖，默认启用。支持最低有效提取数（默认 0 禁用）、最大无效比例（20%）、相对基线最大下降（50%，0 禁用）、连续失败次数（2）、恢复正常次数（2）、调度到期宽限（10 分钟）。阈值分别有上限；页面编辑未保存时离开/重新读取需确认。保存响应未知时重新读取核对，旧 revision 不能重复保存；本地编辑保留。

基线必须明确选择同 owner/方案的一次完整、已提交、有有效记录的实时正式运行，留空取消。不会自动学习失败、有限覆盖或离线数据。未配置基线不推测骤降，明确最低数量仍可独立判断。页面提供基线运行入口和数量/覆盖摘要；基线不是当前数据表总量。

## 证据与归因

- `v22_quality_policies` 保存当前策略与基线事实，`v22_quality_evaluations` 按正式 run_id 唯一保存评估，`v22_quality_issues` 按 owner/collector/code 唯一聚合同类问题。只读取 v2.2 正式运行，不访问旧磁力表、旧任务、试采、离线回归或插件。
- 独立 `v22QualityWorker` 每 2 秒观察一条尚未评估的终态运行，按完成时间/id 排序，评估与问题状态同事务提交。默认会补评已有新域正式历史；有积压时页面显示待评估数。策略修改前已结束的未评估运行只记录 policy_changed，不重判旧证据。观察失败重试，不影响正式运行提交。
- owner/collector advisory lock 串行策略、观察、调度问题和恢复确认；唯一 run_id 防重复计数。正式 writer 无需调用质量观察，质量存储失败不会回滚已提交正式数据。
- SQL 只返回提取有效/无效数、失败字段稳定键与步骤角色，过滤到正式输出角色及已选择的 output_indices；失败字段额外包含实际失败角色。原文、字段值、凭据不进入质量 API，SQL 静默上下文避免记录原文。
- 使用实际提取量，不使用新增数量；全部 unchanged 仍可正常。明确数量偏低、同范围有效量骤降、无效比例过高、字段失配、浏览器/RPC/会话故障、连续失败与有限覆盖分别归因。取消不当作失败，不提供恢复证明。
- 对记录量的相对比较要求相同入口、HTTP 请求、输出表/Schema/映射、输入范围/预算和路径/循环配置；选择器和字段提取规则修复允许继续比较。版本 ID 与 output check_id 不作为范围身份。实际列表页数和数量保留供核对；范围不兼容明确 incomparable，不做数量骤降判定或恢复。
- 调度独立每轮扫描最多 10 个方案，游标轮转避免只观察前几个。配置/版本阻断、容量跳过与 enabled 计划超过到期宽限归为调度问题。用户主动暂停或正常重叠跳过不新增问题；反复读取同一阻断不累计虚假的“出现次数”。暂停不会证明既有问题恢复。

## 恢复条件

问题状态为 `open → ready → resolved`。ready 仅表示有足够候选证据，需要用户核对并确认；不是自动关闭。

1. 后续运行必须完整 succeeded、实时访问、正式提交，并使用当前发布版本。有限覆盖、失败、未提交、无基线可比性不能证明恢复。存在基线时必须可比较，并满足当前策略全部阈值。
2. 恢复运行要在异常发生后开始；已有在途运行晚到的成功不冒充修复验证。非调度问题还要求与原异常的范围身份一致，修改输出/Schema/范围不能静默关闭原问题。
3. 达到配置的连续正常次数才 ready；失败/不完整/不兼容结果重置计数，取消保持既有计数但不增加。修改或停用策略不关闭问题；策略修改重置尚未解决问题的恢复证据。
4. 调度问题额外要求真实 `trigger_source=schedule` 运行，且当前计划启用、下次时间有效、无配置/容量阻断。手动成功不证明调度恢复。
5. 确认时检查问题 revision、候选 run_id、计数、当前发布版本/策略/范围，最新非取消正式结果仍为此证据，且没有活动或未评估运行。锁住 collector，避免新触发插队；调度问题先锁计划再锁方案，与调度保存/触发保持相同顺序，防止暂停和确认交错。有新结果或调度变化返回冲突。
6. 重复确认同一已解决问题和同一恢复 run 只返回原结果。以后同类异常再次出现会重新 open，保留首次运行、累计次数和最新证据；不重复创建同类问题行。

只有范围相同的证据能解决原问题；主动变更数据目标/Schema 的问题处置与审计仍需 D05 扩展，不提供未经验证的强制关闭按钮。

## 页面与接口

| 接口 | 页面用途 |
| --- | --- |
| GET /collectors/{collector_id}/quality | 策略/基线、最新评估、待评估数，一致只读快照 |
| GET/PUT /collectors/{collector_id}/quality-policy | 读取/保存阈值与明确基线，独立 revision |
| GET /issues | active/open/ready/resolved/all，方案筛选、创建时间/id 游标分页 |
| GET /issues/{issue_id} | 实际异常/恢复证据与影响 |
| POST /issues/{issue_id}/resolve | 核对正式证据后确认恢复 |

新 `/app/issues` 和 `/app/issues/:issueID`；首页、健康卡片及方案工作台均可进入。健康摘要保留尚未确认的质量问题，即使最近运行成功；卡片最多 6 条，完整问题见待办页。首页质量基线按方案配置，不显示全局虚构趋势。

所有读取/修改限定 owner，API 5 秒、前端请求 8 秒，不返回原始规则/输入/记录值。不自动网络验证、重新运行、发通知、派发插件或关闭问题。
