# 按键Join与批次屏障 O5-03b 实施与验收记录

日期：2026-10-14。本轮开发交付CO-O5-03b首版：有限运行内按键Join与批次数组收集。只修改scrapio主平台，无浏览器协议变化。O5-03a联合输入保留；O5-04～09未实现，O5-R真实验收未完成。

## 1. 产品场景与模式选择

| 模式 | 示例 | 执行时机 |
| --- | --- | --- |
| single | 一份榜单进入详情阶段 | 每条完整输入到达 |
| union | 多个榜单的电影地址进入同一个详情采集器 | 各来源完整输入到达即可执行 |
| join | 来源A提供movie_id/url，来源B提供movie_id/分类，配成电影请求输入 | 本运行全部上游成功并完成派发后，按键生成工作项 |
| batch | 来源A提供电影地址，来源B提供ID，分别收成urls/ids数组，发给固定地址的后续请求 | 本运行全部上游成功并完成派发后，形成一个批次工作项 |

Join与batch不改变采集器的职责：采集器仍执行“结构化输入→请求/浏览器动作→提取→输出”；汇聚属于任务输入准备。若只需把两个榜单汇在一起逐条访问，应选择union。只在需要配对字段或整体请求时选择Join/batch。

批次首版提供`collect`，不提供sum、avg、group-by表达式或任意SQL。不同来源数组是独立集合，不保证按数组下标对应；需要对应关系时先按明确键Join。窗口为一次有限运行，不提供跨运行、持续订阅、水位线、迟到补偿、外连接或多对多笛卡尔积。

## 2. 配置与契约

任务编辑器的「阶段输入」新增「按键配对」「批次收齐」。每条连接继续选择端口、过滤、数组展开和字段映射；汇聚模式允许映射部分输入字段，片段类型仍严格校验。切换模式不自动改写已有映射，需要用户重新确认。

```json
{
  "input_mode": "join",
  "gather": {
    "key_fields": ["movie_id"],
    "missing": "reject",
    "max_rows": 100,
    "max_bytes": 262144
  }
}
```

Join约束：

- 仅非入口，2～5条来源连接；1～5个输入匹配字段，各来源必须提供。匹配键必须是非null标量，不支持数组或JSON键；按类型校验后的规范值匹配，不隐式转换数字/字符串。
- 每条连接、每个匹配键最多一条结果。重复键记`JOIN_DUPLICATE_KEY`，该键不执行；不随意选择首条/最后一条，也不做多对多展开。
- 除匹配键外，每个目标字段只能有一条来源连接；冲突在保存/发布前拒绝，避免来源到达顺序决定覆盖结果。
- 缺失来源：`reject`记`JOIN_MISSING_SOURCE`及invalid分组，`skip`记skipped分组；两者都不执行该键，并如实标记不完整。其他完整键可以继续执行。
- 所有必填输入必须由某条来源映射或采集器输入默认值提供；所有片段配对后才填默认值、校验完整输入和请求范围。

Batch约束：

- 仅非入口，1～5条来源；`gather.key_fields`省略或为空，`missing=reject`。
- 每个被映射的目标是数组字段，来源映射单个元素。若来源本身是数组，可先用原连接展开。各目标字段只由一条连接提供，不隐式拼接不同来源的同名字段。
- 固定URL/参数放在采集器输入默认值中；收齐后应用默认值并校验完整请求。正常确认空态的来源得到空数组，目标字段需要允许空数组；否则形成具体字段错误。
- 每个数组沿用最多100项、完整输入最多64KiB及现有类型/敏感字段约束。缓冲预算较大不等于可以突破这些输入约束。
- 批次顺序按已持久回执身份固定，只保证同一运行恢复的一致性，不宣称网页顺序、跨来源位置关联或跨运行相同顺序。

「预览下游输入」在Join/batch模式只预览当前来源的类型化片段，不代表完整配对成功。完整键、最终批次和错误在试采「配对与批次诊断」确认，正式业务写入仍为0。

## 3. 完成、迟到、预算与失败

所有来源都以冻结运行和派发回执为边界。只有全部上游阶段终止、各自待派发计划耗尽，才检查来源是否都完整成功并封口；不会因队列暂空或首个来源完成就释放汇聚工作。仍活动的慢来源可以继续到达，不依赖内存超时配对；暂停和未知动作不是完成，需先恢复或处理回执。

上游失败、部分成功、受限或来源映射无效时，整次汇聚生成`GATHER_INCOMPLETE_SOURCES`诊断，不执行已收集的半个批次。其他独立分支按原规则继续。正常空态并且已提交完成检查点的来源属于成功：Join对其他来源已有的键按缺失策略处理；所有来源全空时Join无工作，batch生成空数组输入并按字段契约检查。

汇聚预算每阶段配置，行数1～1000、字节1024～4MiB。缓存行和JSON字节在数据库运行锁内计数，达到预算时后续回执记`GATHER_BUFFER_BUDGET`，不执行不完整批次。封口后的完整输入与来源ID快照还受同一字节预算，防止默认值放大，超出记`GATHER_SEALED_BUDGET`。

全运行工作项、输出、派发、时长、存储及并发保护继续生效。封口后工作项预算不足的分组标记limited；队列容量不足保持pending，按容量继续派发，pending分组阻止阶段提前结束。缓存回执不占可运行工作项队列，因此单槽队列也能收齐生产者。用户取消/总时长耗尽时pending分组随运行标记cancelled/limited，已提交结果保留。

缺失/重复键等分组错误会形成部分完成，不伪装为采集器成功。`on_error`仍处理采集器工作项失败；本轮分组校验错误直接记入汇聚诊断，不生成错误工作项或隐式暂停。处理来源/规则问题后应重新运行包含全部必要上游的范围。

## 4. 持久化、恢复和补采

迁移`2026_10_14_002`新增：

- `co_stage_runs.gather_sealed`：已完成来源封口，不再次计算分组。
- `co_gather_groups`：固定分组键、完整输入、成员回执ID、pending/delivered/invalid/skipped/limited/cancelled状态、错误及子工作项，`(stage_run_id, group_key)`唯一。

已接收片段保存在原`co_dispatches`，状态buffered；原派发计划按已持久回执推进，从而允许生产者结束。封口、分组、输入快照、工作项、来源和lineage在持有运行锁的同一数据库事务中提交，任何一步失败整体回滚。封口后待派发分组继续持久等待容量，重复轮询不重复创建工作项，已有租约/检查点保护不改变。

每个汇聚工作项都关联全部成员输出的lineage，运行输入source中记录group_id/模式/键。分发页展示原片段回执，汇聚页展示最终工作项；不把多个来源数量混同于实际工作项数量。运行输出及汇聚证据保留，现有清理只清理未引用来源资产；汇聚副本、索引等不计入原业务输出JSON配额，需要继续使用部署磁盘监控，行数/字节预算是单运行保护。

局部补采：

1. 汇聚阶段可选择已经组装完成的历史工作项输入，或显式确认的完整表快照，作为新运行根输入；不重做原配对，范围仍标为局部。
2. 不接受用单条上游输出直接补采Join/batch；一条片段不能冒充完整输入。
3. 从某个分支重跑时，若其共享后代Join/batch缺少被裁剪的必要来源，直接拒绝；需选择包含全部上游的起点，或补采汇聚后的完整输入。
4. 版本、输入、命名端口和映射仍冻结，旧运行不变；原试采的补采继续试采隔离。

新诊断接口`GET /api/v4/runs/{run_id}/gather-groups`按所属用户校验、游标分页。运行详情增加buffered_rows、gather_counts与gather_sealed；映射预览增加可选input_mode和fragment_only。能力接口明确支持四种模式、窗口、预算、重复键拒绝及collect首版，OpenAPI生成链追加`co-o5-gather.cjs`。
