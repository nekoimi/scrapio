# D01：失败输入带入修复

状态：2026-10-10 开发收尾。短时边界用例、相关 Go 包编译、Vue SFC 和局部类型检查已通过；真实迁移、并发及页面验收仍待发版。

## 1. 使用流程

正式运行 `failed/partial` 时，运行详情提供“修复方案”。默认读取这次运行的原发布版本、失败步骤和保存文档；也能从页面树或页面证据点击“带此页面修复”，由链接传递文档 ID，不让用户手输。

准备页显示原版本、实际失败步骤/阶段、结束原因、可带入的输入步骤/角色和需核对字段。**实际失败步骤与所选输入步骤分别保存**，显式选择其他页面不会把它伪装成失败发生位置。原文未取得、被清理、损坏、超限或格式不支持时明确说明；修复上下文仍可建立，但不会自动用别的页面替代，也不会访问网站补原文。

| 修复方式 | 对草稿的影响 |
| --- | --- |
| 继续当前草稿 | 原名称、入口、规则、revision、输出和发布指针全部保留；只建立修复来源与离线快照。已有未发布修改不会被覆盖。步骤被删除/角色变化时明确提示核对或另建，不隐式恢复规则 |
| 从失败版本另建 | 从该运行的冻结定义、入口和入口类型建立独立草稿，revision=1；数字规则保持原精度。去掉原方案专属的 output 确认，必须重新确认目标表、映射与输出检查；不复制发布、样例、调度、凭据或运行 |

两种方式均以准备时来源草稿 revision 为创建条件。草稿发生并发修改时返回 `REPAIR_CONFLICT`，刷新上下文重新选择，不覆盖服务器或用户已有修改。归档来源只允许另建，不恢复原计划或取消已有运行。

创建后进入 `/app/collectors/:id?repair_id=...`，修复面板可再次读取持久来源。显式点击“带入保存输入并定位步骤”才接入提取预览；面板使用**当前草稿** revision 验证，显示准备时与当前 revision。字段定位复用 JSON/网页配置面板，没有浏览器会话时可定位定义中的字段文本。规则/格式/角色不匹配时不将历史输入当成当前步骤通过的证据。

本轮仅完成失败输入到草稿的交接。正常保存、预览、单样例检查、试采、输出确认和发布沿用已有路径；完整样例回归/版本比较在 D02，质量基线和有条件解除问题在 D03。建立修复草稿、成功离线预览均不等于正式恢复，不自动发布、重跑或解除健康提示。

## 2. 原文与失败证据

自动选择限定为同一运行最新 attempt、失败步骤及 list/detail 角色的保存文档，优先带无效字段或空匹配文档，之后按事件顺序选择。输出验证只报告总体失败时，从**原运行冻结 output** 推导输入步骤/角色；action/entry 等未取得文档的失败不自动替换为之前的成功页面。

页面树的显式选择可以指定该运行的其他保存页面，来源仍显示真实文档/步骤，服务器校验 owner 和 run 关联。输入哈希、文档 ID 与 HTML/JSON 格式核对；复制上限 1 MiB。字段诊断只返回最多 64 个去重无效 field_key，不在上下文返回原值、规则、请求、凭据或 lease。

可用输入复制为新的 `v22_captures`，`source=offline`、`network_accessed=false`，目标 collector/revision 绑定到修复草稿，保留原内容哈希及源 URL/BaseURL。副本与原文保留独立，不需要旧编辑会话；原文以后清理不会自动改写已经复制的输入。副本随后缺失、清空、损坏或超限时，读取上下文更新可用状态，不自动重新取样。

共用 Runner 还补齐了“已取得有效输入、提取器直接报错”的失败文档：在原有输入哈希、来源与大小预算内保存输入和 `error_code`，不生成正式候选。文档数量表示取得输入，失败状态继续保留。证据保存沿用 emit 的取消与正式 lease fencing；保存失败立即结束，不继续派发或写入。未取得文档、超预算或取消/lease 失效不伪造可用输入，旧失败运行也不会回填网站页面。

## 3. 接口与事务

OpenAPI：[接口契约](阶段0接口契约草案.yaml)，版本 `0.19.0-d01`。

- `GET /api/v3/runs/{run_id}/repair-context?document_id=...`：只读准备，不创建资源。
- `POST /api/v3/collectors/{collector_id}/repair-drafts`：必须确认 `run_id/document_id/mode/expected_revision/confirmed` 与 `Idempotency-Key`；`document_id` 可为空。返回 201 表示修复资源已保存，绝非网站执行成功。
- `GET /api/v3/repair-drafts/by-key`：用原请求键恢复结果，不重复创建。
- `GET /api/v3/repair-drafts/{repair_id}`：读取持久交接来源和离线输入引用。
- capabilities 增加 `supports_repair_drafts`，不依赖浏览器就绪。正式与试采文档 schema 增加可选 `error_code`。

迁移 `2026_10_10_009` 新增 `v22_repair_drafts`，关联 owner、来源/目标方案、原运行、可选离线输入、原请求键、输入 fingerprint 和上下文。原文直接使用已有输入快照表，不新建浏览器任务或读取旧数据域。

每个 owner 最多 100 个修复上下文；owner 事务锁避免不同请求键并发突破容量。相同 key 绑定来源方案、运行、选择文档、模式、revision 及确认；同输入返回原上下文，异输入 409。先读已创建请求，再校验新请求草稿，避免成功响应丢失后因为草稿更新而另建。创建上下文、复制原文和另建草稿在同一事务；失败不留下半个副本。来源方案行锁与现有草稿写入协调，原运行、原发布版本和正式记录不更新。

认证后仓储 deadline 为 5 秒，前端修复请求为 8 秒。大文档和定义 SQL 参数日志关闭。超时/500 保留原 key，通过 GET 恢复；页面刷新或离开提醒，sessionStorage 保留未确认 key。结束本地等待不会删除服务端资源。创建后的草稿 URL 带持久 repair_id，可再次打开；修复容量/保留与清理策略后续归 D05，本轮不自动清理保护来源或提供问题生命周期。
