状态：开发收尾，2026-10-10。真实 PostgreSQL 迁移、服务重启、浏览器和页面交互验收留待发版；本轮只做短时契约、边界和编译检查。下一项为 C03 查询、视图和导出。

## 使用流程

从方案概览打开“调度与 API”（`/app/collectors/:id/schedule`）。先选择一个明确的发布版本，确认允许访问的 origin 和正式预算，再配置定时计划或创建 API 凭据。二者分别冻结版本、来源和预算；以后编辑草稿或发布新版本都不会自动切换。

计划采用五段 Cron（分、时、日、月、周）与独立 IANA 时区。例如 `0 9 * * *`、`Asia/Shanghai` 表示每天当地 09:00。使用现有 cron 库的标准日/月/周语义；日期与星期同时指定时按标准 Cron 的“或”处理。时间统一以 RFC3339 返回；页面提示具体 IANA 时区，下次时间按当前设备时区显示。不支持秒级、`@every`、表达式内时区或 `Local`。Go 内嵌 tzdata，运行环境不依赖系统是否安装时区数据库。

保存不会发布规则。启用/恢复时从保存完成附近的当前时间算下一时点；暂停会清空 `next_at`，不取消已有 queued/running，不修改草稿或正式数据。改变访问范围和预算需要重新勾选真实访问确认。目标表不兼容后仍能暂停已有范围，恢复需要重新校验目标与发布版本。

## 持久化与触发边界

迁移 `2026_10_10_006` 新增三个独立表，并将 `v22_runs.trigger_source` 约束扩展为 `manual/schedule/api`。不迁移或领取旧 cron/workflow 任务。

| 表 | 保存内容 | 限制 |
| --- | --- | --- |
| `v22_schedules` | 每个方案一个计划、配置 revision、冻结 input、启停、下一时点、最近决定 | owner 与方案绑定；保存 revision 乐观检查 |
| `v22_schedule_events` | 配置操作、到期时间、接受/跳过/停用决定、run_id、遗漏时点合并标志 | 每个方案保留最近 100 条 |
| `v22_api_keys` | owner/方案、名称、SHA-256 token hash、冻结 input、创建/撤销时间 | 每方案 5 个有效、100 条总历史；不存密钥明文 |

独立 `scheduleworker` 每秒查询数据库，使用数据库时间、行锁和 `SKIP LOCKED` 领取到期计划，每轮最多处理十个。正式执行仍由原 `runworker` 完成，长采集不会阻塞计划扫描。

创建运行、推进下一时点、记录触发决定处于同一数据库事务。运行键由方案 ID、配置 revision 和原到期时间生成。数据库/进程异常导致事务未提交时，到期槽仍存在；重新处理该槽不会重复入队。能力检测不在持有计划事务时访问浏览器；执行器会在真实访问前复核能力，入队成功不等于执行成功或数据提交成功。

停机遗漏时点最多合并为一次触发，再把下一时点推进到当前时间之后；不逐个回放停机期间的任务。日志 `coalesced` 表示已跳过多个遗漏时点。

同方案有活跃运行时，`skip` 记录 `skipped_overlap` 并推进时点；`queue` 最多保留一个 queued 请求，已有 queued 再触发则跳过。该判断涵盖手动、定时、API 运行；新增手动运行仍沿用 B06 的账户级容量。账户最多三个 queued/running、1000 条运行历史，容量已满记 `skipped_capacity`，不无限堆积。当前执行器单任务串行；排队运行保持自己创建时的完整发布定义和范围，后续暂停/换计划不改写已入队内容。

版本/方案不可用或目标 Schema 不兼容时，到期计划会停用并记录原因；临时数据库故障回滚，后续重新处理。归档后的方案拒绝新运行，已启用计划在下一次到期扫描时标记停用。运行中断沿用 C01 的租约隔离和诊断终态，不新增自动续跑或动作重放。

## 管理接口

以下接口使用现有管理员 JWT，权限按 owner 和 collector 约束。

| 接口 | 行为 |
| --- | --- |
| `GET /api/v3/collectors/{id}/schedule` | 读取计划；未配置为 `data:null` |
| `PUT /api/v3/collectors/{id}/schedule` | 写入 `expected_revision/enabled/cron/timezone/overlap/input` |
| `GET /api/v3/collectors/{id}/schedule/events` | 最近 100 条配置和到期决定 |
| `GET /api/v3/collectors/{id}/api-keys` | 名称、ID、范围、创建/撤销时间；不返回密钥或 hash |
| `POST /api/v3/collectors/{id}/api-keys` | 客户端 UUID、名称和冻结 input；密钥仅返回一次 |
| `DELETE /api/v3/collectors/{id}/api-keys/{key_id}` | 幂等撤销；不取消已创建运行 |

保存丢响应时，仅当当前 revision 为 expected+1 且完整配置与原请求一致，重试才返回原结果，避免重算并推迟下一时点。其他冲突返回 409。前端保留未确认保存的完整请求及凭据创建 ID，可重新查询；放弃本地编辑需明确确认，不默默覆盖。

凭据创建不支持重新读取明文。若创建响应丢失，使用客户端 UUID 在列表找原凭据，撤销后重建。密钥只在页面内存显示，不进入 localStorage/sessionStorage；仅将未确认凭据的 UUID 保存到 sessionStorage。页面在编辑、未确认请求和未保存密钥时保护离开。创建响应设置 `Cache-Control: no-store`。

## API 触发

`POST /api/v3/collectors/{id}/api-runs` 使用专用凭据 `Authorization: Bearer sap_…`，不使用管理员 JWT。此路由在受保护 `/api` 子路由前单独注册，专用密钥只能调用这个操作，不能读取管理、页面或数据接口。

```bash
curl -X POST 'https://YOUR-SCRAPIO/api/v3/collectors/123/api-runs' \
  -H 'Authorization: Bearer YOUR_TOKEN' \
  -H 'Idempotency-Key: request-001' \
  -H 'Content-Type: application/json' \
  -d '{}'
```

请求体 `{}` 使用冻结预算；也可以提供完整 `budget`，每个值必须在正式运行边界内且不大于凭据上限。不允许覆盖 version、origin、入口、规则、目标表、HTTP header 或其他字段。原预算也可作为完整覆盖提交，幂等指纹按有效输入计算。

凭据只授权所属 owner 和方案的固定版本。凭据验证与入队处于同一事务，共享凭据行锁；撤销取得排他锁，成功撤销后不再接受新请求。Token 为 256 bit 加密随机值，仅保存 SHA-256 hash。

每次请求必须有 1～80 字符 `Idempotency-Key`。键按凭据 ID 命名空间隔离；同键、同有效输入返回原 `run_id`，包括原运行已经完成时，不创建新运行；同键不同输入返回 409。已撤销密钥不能查询原触发。内部 `api:`/`schedule:` 键前缀保留，不允许新手动请求占用。

API 默认使用最多一个等待任务的排队策略，账户活跃容量保持一致。容量/方案重叠冲突为 409；返回 202 仅包含 run_id、collector_id、version_id、status、trigger_source，不暴露发布定义、请求头或采集结果。重复请求用于恢复未知入队结果；实际结果由管理员在运行中心查看。固定版本不兼容为 409，真实访问前的能力故障由运行诊断报告。
